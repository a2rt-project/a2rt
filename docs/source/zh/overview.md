# 协议概览

当前架构草案以统一时间和共享容量为基础，组织需要共同处理的信息，并允许不同同步组独立推进。它适用于网络、本地通信或具身智能等部署；配置须匹配实际生产、处理、传输和消费能力。

## 从时间到内容

| 层次 | 负责什么 | 绑定关系 |
| --- | --- | --- |
| 标准根时钟 | 共同原点、频率、标准帧字节规格、每刻容量 | 每个 epoch 恰好一个 `clock_id=root` |
| 子时钟 | 通过父周期比例与偏移组织节拍 | 一个父时钟，最终可达 root |
| 信息同步组 | 共同窗口、交付策略、组容量和接收队列上限 | 绑定一个时钟 |
| 轨道 | 角色、方向、来源、格式和内容策略 | 通过 `sync_group_id` 绑定一个组 |

时钟与同步组不定义角色或方向。轨道名称也不能代替显式配置。不同组可复用同一时钟，但不会因此自动互相等待。

## 三种“帧”

- **标准帧单位**：计量字节容量的单位，包含 A2RT 自身封装开销。
- **轨道数据帧**：一条轨道在所属组的一个周期内提交的一份逻辑数据。
- **组信息帧**：同组同周期中，不同轨道数据帧的集合，可占用多个标准单位。

每轨每周期最多一个数据帧。多来源或双向两端共享这个名额，不能各发一帧；分片与原帧重传不增加名额。同一位置不能用不同内容覆盖原帧。数据帧也不等于一个网络包、一个音频采样或一次模型生成。

## 同步的范围

Profile 定义哪些成员对哪个接收端必要、怎样判断完整、空值与保持是否有效，以及超时后如何处理。Core 根据这些结论推进交付。输入与输出同组时，各接收端只等待适用于自己的成员，不等待反向内容或自己刚发出的数据。

同步组没有强制“全部成员无条件等齐”的含义。不同组独立推进；请求的执行反馈可以进入后续窗口，仍须保留因果引用。实际播放时刻由 Profile 映射，不能直接把窗口坐标当成设备播放时刻。

## 系统通知与领域契约

每个会话配置必须且只能有一条 `role=system`、`direction=input` 轨道，由可信环境或协调器发布。Profile 决定它同组或独立，以及通知的事件名称、字段和 Schema。模型内容与可选的结束请求走 assistant 输出轨道。

Core 不强制统一的工具事件、空事件或生成标识。Profile 定义这些内容，以及播放、恢复、同步完整性和内容校验。配置在 epoch 内冻结，变更重新协商并保留历史解释。

## Canvas 是一个实例

Canvas 选择六条领域轨道，加上唯一的 system 输入轨道，并采用同步交付、每 actor 同时一个任务与异步录像。其他 Profile 可以采用不同轨道与领域规则。[查看 Canvas 适配要求](profiles/canvas.md)。
