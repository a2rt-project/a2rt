# 设计接入步骤

当前阶段从架构配置和 Profile 契约开始设计接入。Canvas Realtime 已有本地 mock 和配套定义，可作为具体实例检查；通用线协议和生产运行时尚未发布。以下步骤用于设计接入。

## 1. 明确参与方与实际能力

指定智能体端、环境端、可信协调器、发布来源与接收端。根据采集、编码、传输、解码和处理能力确定目标工作范围。分别约定两个方向的发送前准备、校验与发送侧恢复责任，接收端验收后才开放消费。传输成功、模型已消费与用户已听到分别记录。

## 2. 设计根时钟与子时钟

配置唯一 `root` 的原点、`frequency_hz`、`standard_frame_bytes`、`standard_frames_per_tick`。子时钟采用正整数父周期和非负整数偏移。逐级计算所有边界到整数根刻度的精确映射，不能舍入。

例如根为 1,000 Hz，子周期为 100 根刻度，则子时钟为 10 Hz；不是每个根刻度都必须发送消息，也不代表 1 ms 的端到端保证。信息时钟匹配真实生产和消费节拍；内部 20ms 重试不要求提高模型信息频率，新采集观察仍等待合法周期。

## 3. 划分信息同步组

为需要共同窗口的内容设置 `sync_group_id`、`clock_id`、`start_tick`。用 `delivery_policy` 声明所选 Profile 的交付规则，用 `limits` 确认整个组的编码容量和每个接收端的队列上限。共享根容量，检查重叠窗口、突发与持续总量。

## 4. 注册轨道与格式

每轨引用一个同步组、一个格式，声明角色、方向和允许来源。格式目录使用 `media_type + constraints`；JSON 的 `schema` 与 `schema_ref` 二选一或按 Profile 使用通用 JSON 规则，不能同时存在。双方确认能力后在 epoch 内冻结。

必须配置唯一的 system 输入轨道。双向两端如需同周期各发一帧，应拆成两条普通单向轨道；不能复制 system 轨道。

## 5. 写清 Profile 的四项职责

明确播放映射、超时恢复、完整性判断和内容校验的责任方与规则；同时声明 system／assistant 的事件、Schema、输出与任务边界。异常时可以静默丢弃，也可以按契约通知、恢复或终止；Core 不强制错误码、逐帧 ACK、补包请求或专用错误轨道。写清通知来源、载体、作用范围与失败处理，以及丢弃后缺口和后续交付规则。协调器实际处理中断、关闭和清理，不等待通知交付。

## 6. 验证设计，再验证实现

阅读[完整配置示例](examples.md)，检查树、引用、整数映射、单帧名额和共享预算。实现阶段还需分别验证媒体内容、分片、队列、迟到、冲突、恢复和真实时延。可对照 [Canvas Realtime](profiles/canvas-realtime/index.md) 的 10Hz 观察与 L16 字节契约。本站的文档检查不等于运行时一致性认证。
