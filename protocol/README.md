# A2RT：智能体实时多模态交互协议

**Agent-to-Real-Time Protocol**。状态：当前架构设计草案；日期：2026-11-16。

## 协议定位与分层

**A2RT 是面向智能体与环境的实时业务信息交互协议，提供可配置的多轨信息通道和统一的时间组织契约。** 它约定双方交换什么信息、以什么节拍交换、哪些信息需要同步，以及信息达到什么条件后可以被消费。

A2RT 可以理解为面向智能体信息的虚拟化通道：轨道表达信息角色、方向、格式和来源，时间与容量约束组织信息的生产、交付和消费。环境按约定交付可消费的观察，模型输出的音频、动作或其他内容由环境按契约接收和执行。应用语义由 Profile 定义，具体通信方式由 Binding 落实。

| 层次 | 定位与职责 |
| --- | --- |
| Core | 通用的信息组织规则：身份、轨道、时钟树、信息同步组、格式声明、时间窗口、交付状态和资源约束 |
| Profile | 具体应用的交互契约：内容与事件语义、消费条件、同步完整性、播放与执行规则，以及异常处置和通知方式 |
| Binding | 将契约映射到具体承载方式：序列化与封装、连接与来源绑定、传输及重组、发送调度、容量和队列约束，复用底层协议能力 |

Core、Profile 和 Binding 分别描述规范职责；发送端、接收端、适配器和运行时是落实这些职责的执行主体。同一进程可以实现多个层次，职责不会因此合并。详细边界见[第 03 章](./03-core-profile-responsibilities.md)。

标准根时钟提供共同时间刻度与容量基准，子时钟定义更新节拍，信息同步组组织共同窗口，轨道承载具体角色、方向与内容格式。播放、恢复、同步完整性判断及内容校验由具体 Profile 定义，由发送端、接入层和运行时实现；这些职责不能因此转交给模型。

时钟配置依据实际生产、处理、传输和消费能力确定，运行时与传输绑定落实节拍和预算。“实时”通过已确认的节拍与交付条件表达；“高速”是正常路径承载合格业务信息所追求的运行特征，实际吞吐和延迟取决于部署能力、配置及实现，协议本身不作无条件保证。同步交付与独立交付由同步组配置及 Profile 规则组织；同一时钟可以供多个独立同步组复用，不自动形成全会话等待屏障。

核心不绑定项目、画布、模型厂商或 MCP 服务。Canvas 是其中一个应用 Profile：六条业务轨道、10Hz 交互、同步观察和每 actor 同时一个任务都是该实例的选择，不构成其他 Profile 的强制规则；机器人、传感器及其他环境可以定义各自的应用契约。

## 责任原则：谁发送谁负责

**A2RT 默认承载符合约定的业务数据。发送端负责按照 Profile，将信息组织成接收方可消费的信息单元；接收端负责验收与消费。** Profile 定义合格标准、交付条件和异常策略；需要纠错或恢复时，发送端承担发送侧责任，双方运行时按约定协作。

这个原则适用于两个方向：环境发送观察时，负责采集、拼装、对齐和发送前校验；模型服务发送输出时，由其适配器组织音频、操作及时间关联。发送端包含相应运行时，不要求模型本身处理分包或重传。接收端仍做必要的重组、去重、解码与校验，发现问题按 Profile 丢弃、通知或进入其他约定流程；需要补交时由发送端重发或重新采集。接收端不负责猜测或修补发送内容的业务含义。

## 默认业务通道与异常处理

正常交付路径以发送方已完成准备和校验、数据符合契约为前提。“默认符合约定”是责任契约，不是绝不发生故障的保证，也不取消接收端的必要校验。合法的业务失败结果，以及 Profile 选择发送的异常通知，只要符合其内容契约，都可以作为轨道数据。

**Core 不强制定义错误控制消息、错误码、逐帧 ACK、补包请求或专用错误轨道。** Profile 可以约定直接丢弃、不发送通知，也可以通过自定义轨道、另建通知通道或其他方式通知，并决定是否恢复或终止。Binding 落实这些选择，并可复用底层传输已有的可靠性能力。

异常策略不能放宽 Core 约束：丢弃不能伪造成功交付、当前画面或静音；自定义轨道仍遵守每轨每周期单帧和 system 唯一输入约束。轨道外通知不占 A2RT 轨道周期，不得借此绕过业务数据的交付与容量规则。通知范围、同步组缺口和后续交付由 Profile 明确，详见[第 03 章 §1.3](./03-core-profile-responsibilities.md#13-默认业务通道与异常处置)。

## 面向模型的交付边界

A2RT 的意义在于约定智能体何时获得什么信息，以及交付前必须满足哪些条件。环境侧发送端负责观察的准备与交付质量，模型侧接入层验收并处理必要的传输接入；接收后的检查不转移发送端的信息准备与发送侧恢复责任。模型获得的是已满足 Profile 消费条件的信息，负责理解、推理和产生业务输出，无需拼包、修补音画对齐或发起传输重试。具体职责见[第 03 章 §1.2](./03-core-profile-responsibilities.md#12-面向模型的信息交付边界)。

可消费的信息可以是一个流式片段，也可以是 Profile 明确允许并标注缺失的部分观察；不要求等到整段音频、整个会话或所有同步组都就绪。Canvas 选择同一观察内同步交付，其他 Profile 可以采用不同策略。超时后如何处理由 Profile 规定并由运行时落实，不能把未完成的内部处理留给模型猜测。

信息时钟表达实际信息生产与消费的节拍，根时钟及容量配置支撑其调度。内部重试、分片和轮询可以有更细的时间粒度，不应仅为容纳这些步骤而提高面向模型的信息频率；例如实际交互为 10Hz 时，应按每 100ms 组织可消费的信息，再按约定处理异常。

## 核心设计

1. 每个会话 epoch 恰好一个标准根时钟，ID 固定为 `root`，定义根频率、共同原点、标准帧字节规格和每周期容量，共同构成与实际能力匹配的调度基准。配置可适配网络、本地或具身智能等部署。
2. 子时钟通过父时钟、周期比例和偏移形成时钟树，组织不同内容的更新节拍，并与信息同步组预算共同落实容量分配；继承根标准帧单位，不产生额外容量。所有时钟的整数刻度边界和信息帧窗口两端必须精确映射到 `root` 的整数刻度，允许整数偏移、不要求零点全部重合。该 Core 约束不能由 Profile／Binding 放宽，未来比例表达扩展也须保留，不能靠舍入或容差满足。
3. 信息同步组（Synchronization Group）组织需要按共同窗口处理的信息，会话通过 `sync_groups` 登记。核心属性为 `sync_group_id`、`clock_id`、`start_tick`；附属的 `delivery_policy` 承载 Profile 交付规则，`limits` 承载组容量和各接收端队列上限。一个时钟可被多个独立同步组复用，同组是否完整由 Profile 判断，不要求所有成员无条件等齐。
4. 自定义轨道声明角色、输入/输出/双向、内容格式和来源，通过 `sync_group_id` 引用所属信息同步组。角色和方向只定义在轨道上，时钟和信息同步组都不定义这两个属性。
5. 每条轨道在所属信息同步组的每个周期内最多只能有一个数据帧，这是 Profile／Binding 不能绕过的 Core 约束。一个组信息帧汇集不同轨道各自的数据帧，每项分别引用 `track_id`；多来源或双向两端共享每轨的一个名额，分片与原帧重传不增加帧数。各接收端由所选 Profile 判断自己的窗口是否满足同步交付条件；Core 承载该结果并推进交付。请求反馈保留因果引用，不要求双向互相等齐。六轨成为 Canvas 的配置实例。
6. 内容格式统一使用 `media_type` 与 `constraints`，由媒体类型选择对应的 A2RT 约束规则；格式目录保存完整描述，轨道通过 `format_id` 引用。JSON 支持 `constraints.schema` 内联定义或 `constraints.schema_ref` 引用，二者互斥。接收能力的 `accept` 候选采用相同结构，选定配置在 epoch 内冻结。
7. 播放时刻映射、异常后的丢弃／恢复／通知方式、窗口何时完整、内容是否符合 Schema/业务规则均属于 Profile。Core 保留结构、引用、时间坐标及通用状态约束，不强制错误控制消息或统一异常流程。
8. 每个会话配置必须且只能包含一条 `role=system` 的轨道，固定为单向输入，由可信环境／会话协调器发布通知。Profile 选择该唯一轨道与媒体／状态同组或使用独立信息同步组；需要及时通知时推荐独立配置，实际控制处理不等待通知交付。system 与 assistant 的具体事件、语义和 Schema，以及模型输出标识与边界，均由 Profile 定义。Core 不按载荷中的事件名称自动关闭会话或切换配置；协调器按 Profile 维护实际状态。唯一性限制轨道声明，不限制通知数量。
