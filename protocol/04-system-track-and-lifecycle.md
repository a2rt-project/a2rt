# system 输入轨道与输出／会话生命周期

状态：当前架构设计草案；日期：2026-11-16。本章补充[轨道与信息同步组](./01-clock-sync-group-track-model.md)、[格式声明](./02-media-types-and-negotiation.md)及[Core／Profile 职责](./03-core-profile-responsibilities.md)，定义 system 轨道的通用约束。

A2RT 要求每个会话配置必须且只能包含一条 `role=system`、`direction=input` 的系统事件通知轨道。环境或会话协调器通过它向智能体端发布 Profile 定义的系统通知，例如会话开始、结束或中断处理的通知。该轨道的信息同步组归属，以及事件名称、字段、语义及内容 Schema，均由 Profile／接入双方定义，实际信息处理由协调器、适配器和应用执行。模型内容走 `assistant` 输出轨道，其事件、参数、输出标识与边界同样由 Profile 定义。A2RT Core 规定轨道、通用封装和关联机制，不定义统一的 system 或 assistant 内容事件枚举。

## 1. 系统轨道的角色与方向

方向以会话指定的智能体端为参照：

| 内容 | 轨道角色 | 方向 | 发布来源 |
| --- | --- | --- | --- |
| Profile 声明的系统通知，例如会话状态或中断处理的通知 | `system` | `input` | 可信环境／会话协调器 |
| Profile 声明的模型内容，如音频、操作及可选的输出结束标记 | `assistant` | `output` | 模型或代表其实际输出的模型适配器 |
| Profile 允许的模型请求，如暂停、取消或结束会话 | `assistant` | `output` | 模型／模型适配器 |

system 角色在会话轨道配置中有且只能出现一次；每个配置 epoch 都必须满足这一约束，缺少 system 轨道或出现两条及以上均为无效配置。唯一性按整个会话计数，不能按信息同步组、actor 或 context 分别注册一条。Profile 不能省略这条轨道、将其改为可选，或通过不同轨道 ID 创建多个 system 角色轨道。

以下以 `track_id=system` 标识该轨道，轨道 ID 仍由会话登记，不要求固定为字面值 `system`。唯一性按 `role=system` 判断；其 `direction=input` 是固定约束，不能改为 `output` 或 `bidirectional`。模型不能向这条轨道发布事件，也不能通过改变事件名称冒充系统来源。其他普通轨道仍可以按约定使用双向模式。

唯一的是轨道声明，不是整个会话的通知数量：该轨道可跨多个周期持续传送系统通知，但每个周期最多只能有一个数据帧，system 角色和控制用途均不豁免这一 Core 上限。多个获准协调器也不能在同周期各发一帧，须按 Profile／Binding 的发布安排提交唯一数据帧。没有新通知时按 Profile 的空值或缺失规则处理，不能因此删除必选轨道。切换 epoch 时仍保持一个当前生效的 system 轨道配置，历史配置用于解释历史数据，不表示同时启用多条 system 轨道。

```text
环境／会话协调器 ── system 输入轨道 ──→ 智能体端
智能体端 ── assistant 输出事件轨道 ──→ 环境／会话协调器
```

角色和方向只出现在轨道配置中，事件通过轨道引用继承它们，不在事件载荷中另设可覆盖配置的角色或方向。来源绑定仍区分实际发布者，系统通知须来自获准的协调器。

普通画面、领域状态和传感器数据不因由后端生成就成为会话控制事件。本章配套示例使用 Profile 声明的 `environment` 扩展角色承载这些环境数据，将它们与系统轨道分开。

**system 是必选的系统通知轨道，不是 Core 强制的错误报告通道。** 异常可由 Profile 约定直接丢弃、不发送通知，或使用自定义轨道、另建通知通道及其他方式通知。若选择 system 承载某类异常影响，须由可信协调器按其输入内容契约发布；不能新增第二条 system 或将它改为双向。轨道外通知也不能冒充 system 来源、绕过会话状态和配置约束，详见[第 03 章 §1.3](./03-core-profile-responsibilities.md#13-默认业务通道与异常处置)。

## 2. 配置与交付

系统轨道复用 `media_type + constraints` 格式描述及已有轨道结构。格式和内容契约由 Profile 声明；采用 JSON 时，其内容 Schema 通过 `constraints.schema` 内联或 `constraints.schema_ref` 引用，二者互斥。A2RT 不提供或强制一份通用系统事件内容 Schema。

完整配置示例见第 01 章；以下片段引用其中的 `system_control` 信息同步组及 `system_events_v1` 格式。独立信息同步组是该示例 Profile 的选择，不是 Core 要求。该格式是示例 Profile 的本地配置，`example:profile-system-events-v1` 是说明用占位引用，实际接入须由所选 Profile 提供可用定义，不是待补齐的 A2RT 核心 Schema：

```json
{
  "track_id": "system",
  "sync_group_id": "system_control",
  "role": "system",
  "direction": "input",
  "format_id": "system_events_v1",
  "source_binding": ["session_coordinator"],
  "content_policy": "system_events"
}
```

系统轨道和其他轨道一样，在一个配置 epoch 中只绑定一个信息同步组。Profile 决定它与音频、画面或状态共用信息同步组，还是使用独立信息同步组；其期限、空通知处理和同步完整性规则也由 Profile 声明。需要将通知与对应画面／状态共同交付时，可以同组；需要通知不等待媒体配齐时，推荐独立信息同步组。不能为了向多个信息同步组发送通知而复制 system 轨道，跨信息同步组的目标与内容关联由 Profile 表达。

该轨道通过 `sync_group_id` 引用会话 `sync_groups` 中的登记项。组的核心属性绑定时钟和起点，期限与超时规则放入 `delivery_policy`，容量和接收队列上限放入 `limits`；单向 system 输入所适用的接收队列归属于智能体端，不因此在组配置中增加方向字段。

实际中断、关闭和任务清理由协调器／运行时按 Profile 执行，不应等待系统通知配齐媒体或模型理解通知后才开始。通知可以按选定信息同步组的条件交付，但通知已发出不等于处理完成。选择独立信息同步组不要求另建物理连接；Binding 按 Profile 约定落实发送机会、优先级与超时处理。

智能体端的接入层与模型本身应区分：系统通知先按 Profile 被接入层处理，需要模型理解的业务影响再以约定形式交付。通知不要求模型执行补包、去重、重同步或连接恢复，也不需要把每条内部重试日志都送入模型。发送端／接入层自动发起的恢复属于运行时控制，不能冒充 assistant 的实际输出；模型主动提出的业务取消、结束或重新观察请求仍可走 assistant 输出轨道。

系统通知同样遵循“谁发送谁负责”：可信协调器负责准备符合 Profile 契约的通知，接收端负责验收。通知自身也可能缺失或不符合契约，其丢弃、补交、是否再通知及通知失败后的停止条件由 Profile／Binding 约定，不自动产生递归的错误通知。若选择补交，由发送端承担发送侧责任；接收端继续维护实际接收与消费状态。运行时通知不因此成为模型生成的 assistant 内容，也不改变 system 单向输入的约束。

系统轨道所属信息同步组仍绑定一个已声明时钟并使用 `root` 的坐标和容量单位；它不增加角色字段、方向字段或额外根容量。选择同组时，通知作为该信息帧内至多一个 system 轨道数据帧参与交付；是否必需、没有通知时如何表示由 Profile 定义，不能为凑齐而伪造事件或媒体，也不能在已提交的位置追加第二帧通知。原帧分片或重传按原身份重组或去重；新的通知数据帧须使用后续周期，实际中断和清理仍按上一段独立执行。信息同步组归属变更仍须按配置 epoch 规则协商生效。

系统轨道、所选 Profile 版本及其格式应在接收系统内容之前按初始化约定确认，不能等收到无法解码的开始通知后才定义如何接收它。Binding 建立连接与配置交换，Profile 实现确认其通知格式和语义；首次配置握手不依赖某个固定的系统事件名称。若 Binding 使用底层或自行约定的传输 ACK，它只确认其契约规定的传输事实，不代表模型已停止、任务已清理或会话已关闭；Core 不强制另发 ACK。

## 3. 三种结束边界

下表区分会话生命周期与可能存在的领域边界。Profile 可以定义有限轮次的模型生成、连续输出流或其他交互形式；Core 不要求每个 Profile 都具有“一次生成”或“一个操作任务”，也不要求它们统一发送某种结束事件。

| 边界 | 含义 | 不代表 |
| --- | --- | --- |
| Profile 定义的本次输出结束 | 该 Profile 定义的输出单元达到结束边界，例如一次模型生成不再产生新内容；可跨多个信息帧 | 会话关闭、所有音频已播放、工具已完成或鼠标任务已结束 |
| Profile 定义的操作任务结束 | 一次拖动、工具调用等操作按该 Profile 达到其真实终态 | 本轮模型输出结束或会话关闭 |
| 整个会话结束 | 协调器确认该会话停止接纳新的普通交互 | 仅仅一句话说完、某个工具完成或暂时没有数据 |

会话身份、epoch、轨道／信息帧引用及通用消息关联属于 Core 的承载结构。模型输出如何分组、是否需要输出标识、标识字段叫什么以及跨哪些媒体和事件使用，由 Profile 的内容契约定义；Core 不强制 `generation_id` 或统一的任务标识。Profile 的领域标识不能替代通用消息身份，也不能仅凭字段同名就改变会话状态。一次模型输出、一个信息帧和一条传输消息各有不同的边界。

静音、单个分片结束、传输断线或操作结束本身不构成会话结束事实。Profile 定义如何识别其模型输出边界及是否需要报告；适配器按该契约映射真实结果。收到系统中断通知不证明模型已经停止。

## 4. Profile 解释与运行时状态

Profile 定义 system 通知的事件集合、字段与必填项、目标表达、通知阶段及 Schema 版本，并规定接收方如何解释。它可以区分处理已发起、已完成或失败，不能用尚未完成的请求冒充完成事实。通用来源、会话关联和时间信息仍由 A2RT 封装承载，内容字段不得覆盖身份绑定、epoch 或时间坐标。

Core 不保留某组系统事件名称，也不根据载荷中的固定字符串自动关闭会话、中断生成或切换配置。理解 Profile 的服务端协调器负责实际处理，并通过运行时机制维护会话状态；通知传达对应事实或进展。接收方同样按已确认的 Profile 解释内容，不能在未理解其契约时按事件名称猜测动作。

配置生效仍依赖已确认的配置和 epoch 机制，不能仅发送一条自定义通知就绕过协商或重新解释历史数据。运行时确认会话已结束后，不能把迟到旧输出作为该已结束会话的新交互；这一状态约束不依赖某个通知名称。旧数据的记录、对账及新交互建立方式由 Profile／Binding 定义。

Profile 可以采用自定义事件、工具调用或其内容格式规定的结束标记表达模型意图，也可以不提供结束会话请求。若提供，这些内容仍走 assistant 输出轨道，服务端按 Profile 解释并决定是否接受。模型侧处理结果若需要回报，其载荷也由 Profile 定义，不把系统轨道变成双向。输出结束、媒体收齐、播放完成和任务终态分别按契约判断，不能相互冒充。

不同实现需要确认兼容的 Profile 和格式，才能理解彼此的系统通知；支持 A2RT 核心不自动等于支持任意系统事件。以后可另行提供可选的公共系统事件 Profile 供多个场景复用，但不将其变成所有实现的核心要求，本章也不声明该公共 Profile 已经提供。

## 5. 非规范性 Profile 示例

为说明路由，假定一个示例 Profile 自行定义以下内容。**这些名称和字段仅属于该示例，不是 A2RT 核心标准、保留名称或 Canvas 已选定的接口。** 其他 Profile 可采用不同结构和标识，无需实现同名事件。

| 示例 Profile 约定 | 所属内容 | 示例含义 |
| --- | --- | --- |
| `session.started` | system 输入 | 通知协调器已确认会话进入可交互状态 |
| `session.interrupt` | system 输入 | 通知已发起中断处理，不表示目标已经全部停止 |
| `session.resumed` | system 输入 | 通知协调器已确认恢复交互 |
| `session.ended` | system 输入 | 通知协调器已确认整个会话结束 |
| `config.activated` | system 输入 | 通知已协商的配置生效，不替代配置协商 |
| `generation_id` | Profile 内容中的关联标识 | 该 Profile 用于关联一次生成，不是通用消息 ID |
| `output.ended` | assistant 输出 | 报告该 Profile 定义的一次生成已结束；其标识和原因字段由该 Profile 定义 |
| `session.end_requested` | assistant 输出 | 请求结束会话；也可以由其他 Profile 用工具调用等方式表达 |

以下流程中的 system 和 assistant 内容均按上述示例 Profile 解释。表中的名称没有统一的核心载荷 Schema；这组示意也未提供可直接接入的 Profile Schema。

### 5.1 模型结束本次讲解，继续等待用户

```text
system 输入：session.started(session_1)
assistant 输出：音频与画布操作，属于 generation_1
assistant 输出事件：output.ended(generation_1)
用户继续提问，会话 session_1 保持可交互
assistant 输出：下一次生成 generation_2
```

这里不发送 `session.ended`，也不要求 system 为每个 `output.ended` 额外回复一次。用户下一次提问是否触发模型、何时播放剩余音频，均由 Profile 定义。

### 5.2 模型请求结束整个会话

```text
assistant 输出事件：session.end_requested(session_1)
协调器按 Profile 判断是否接受并完成约定的关闭处理
system 输入：session.ended(session_1)（仅在实际结束时）
```

请求被拒绝或尚未处理时，会话不能仅凭模型请求就被当作已经结束。是否返回请求回执及其载体由 Profile 定义；若需要 `output.ended`，它仍是 assistant 的独立输出边界信号。

### 5.3 系统中断正在生成的输出

```text
assistant 正在生成 generation_2
协调器／模型适配器按 Profile 发起中断
system 输入：session.interrupt，目标由示例 Profile 关联为 generation_2
assistant 输出事件：output.ended(generation_2)，原因标记为 interrupted（仅在取得真实结束结果且 Profile 要求报告时）
会话是否暂停、继续或关闭，由 Profile 定义
```

该结束结果可以由适配器依据模型服务的真实终态报告，不要求已经中断的模型再生成一条确认。仅发出 `session.interrupt` 不能伪造示例 Profile 的 `output.ended`，也不能自动产生 `session.ended`。

## 6. Core、Profile 与实现边界

Core 定义会话配置中 system 轨道必选且唯一、单向输入路由、每轨每周期最多一个数据帧、来源约束、通用会话身份、时间及关联机制，保留运行时会话状态与领域输出边界的区别。Profile 决定该唯一轨道的信息同步组归属，并定义 system 与 assistant 的具体事件、参数、Schema 和语义，以及输出标识、请求解释、中断范围、播放停止、任务清理、恢复及关闭规则；协调器、适配器和 Binding 执行并按 Profile 约定通知实际结果，不能豁免数据帧数量上限。Core 不因 system 必选而要求所有异常经该轨道报告，也不强制错误控制消息。第 03 章下放的四项职责保持不变。

Canvas 后续保留六条领域轨道，并配置必选且唯一的 system 输入轨道，由 Canvas Profile 选择其信息同步组和通知内容 Schema；Core 不要求它独立于领域信息同步组。若定义模型输出结束或结束会话请求，可复用 assistant 输出事件轨道。双方事件的具体名称、参数与内容标识均需由 Canvas Profile 单独确定，不能直接把第 5 节示例当作强制接口。其他轨道仍可扩展，system 的数量固定为一条。

实现方按来源与方向路由通知及模型请求，并分别验证 Core 约束和 Profile 内容契约；不能因为载荷都涉及控制，就混用 system 输入与 assistant 输出轨道。
