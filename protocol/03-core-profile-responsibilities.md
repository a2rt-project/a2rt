# Core 与 Profile 的职责边界

状态：当前架构设计草案；日期：2026-11-16。本章与[时钟、信息同步组及轨道](./01-clock-sync-group-track-model.md)、[媒体类型与约束](./02-media-types-and-negotiation.md)、[system 轨道与生命周期](./04-system-track-and-lifecycle.md)共同定义 Core、Profile 和实现方的职责。

A2RT Core 提供通用承载、时间组织、交付状态，并要求每个会话配置必须且只能包含一条 system 单向输入轨道。Profile 选择该唯一轨道的信息同步组归属；system 和 assistant 的具体事件、参数、语义与内容 Schema，模型输出标识和输出边界，以及播放、恢复、同步完整性判断和内容校验，也由具体 Profile 定义，再由协调器、适配器或应用实现。不同场景可以采用不同策略；同一会话的参与方依据确认的 Profile 和配置协作，Core 不为未定义的业务规则猜测默认行为。

## 1. Profile 是什么

Profile 是基于 A2RT 的具体应用规范，例如 Canvas Profile、机器人控制 Profile 或传感器采集 Profile。它可以包含规范文档、机器可读的能力/配置及内容 Schema；实现代码由适配器或应用提供。Profile 不是必须由 Core 执行的脚本，也不要求把全部规则转换为 JSON 字段。

Profile 定义可复用的规则和允许的选择，会话配置确定本次采用的版本、参数及来源绑定。策略可以通过版本化规范或预先约定明确，不必逐帧重复传递。新增 Profile 不需要将领域字段加入 Core。

| 层次 | 负责 | 不承担 |
| --- | --- | --- |
| A2RT Core | 通用身份与配置引用、轨道及流向、时钟树与窗口、信息帧及其轨道数据帧引用、每轨每周期最多一个数据帧、格式声明、序号与关联、交付状态、system 必选唯一及单向输入约束、资源预算 | 定义 system／assistant 事件枚举、内容 Schema 或模型输出标识；强制 system 独立信息同步组；根据载荷名称执行会话关闭等动作；决定播放、恢复或业务内容有效性 |
| Profile | 唯一 system 轨道的信息同步组选择，system／assistant 事件、参数、语义及内容 Schema，输出标识与边界，呈现与恢复策略、同步完整性标准、校验责任及失败处理、任务与领域规则 | 省略或重复 system 轨道；允许同轨同周期多个数据帧；改写 Core 的身份、时间坐标、配置版本和已记录事实 |
| Adapter／应用 | 按 Profile 解码、校验、判断就绪、调度播放、执行操作及恢复，报告实际结果 | 把未执行、未校验或未交付报告成已经完成 |
| Binding | 传输、分片重组、完整性检查、连接与来源绑定，落实已确认的发送节拍、容量及队列约束，提供实际传输状态 | 把传输成功直接等同于领域内容正确或用户已经看到/听到 |

时钟与容量配置承担控制延迟和避免持续积压的职责，选取方式见[第 01 章 §2.3](./01-clock-sync-group-track-model.md#23-频率选取与调度落实)。Core 提供频率、标准帧单位和公共预算的表达与通用约束；Profile／部署根据实际能力确定目标工作范围和配置，Adapter／应用与 Binding 将其落实到生产、处理、发送及消费流程。具体调度算法和异常处置保持可配置，已确认的预算与期限则必须由相应实现履行。

信息同步组的配置按职责分为三部分：核心属性 `sync_group_id`、`clock_id`、`start_tick` 定义身份与窗口；`delivery_policy` 承载 Profile 选定的交付规则；`limits` 承载确认后的资源上限。`limits.max_frame_units` 约束整个组信息帧的编码容量，`limits.receiver_queues` 通过 `receiver_id` 分别约束各接收端队列的 `max_pending_frames`。这些限额由 Core／Binding 落实，Profile 不能绕过。分组只明确责任，不把容量或缓存上限变成可忽略的业务建议。

### 1.1 轨道内容契约与通用身份

| 内容 | 定义方 |
| --- | --- |
| 会话身份、epoch、轨道／信息帧引用、通用消息身份及关联 | Core；用于路由、时间组织、去重和引用，不解释为某次模型生成或工具任务 |
| 时钟整数刻度边界与信息帧窗口两端的根刻度整数对齐 | Core；允许整数偏移、不要求全部零点重合；Profile／Binding 不得放宽，也不能用舍入或内容对齐容差替代精确映射 |
| 每条轨道每个周期最多一个数据帧 | Core；所有来源和方向共享上限，Profile／Binding 不得豁免；分片和原帧重传不增加帧数 |
| assistant 事件名称、参数、工具调用／空事件表达及单帧载荷结构 | Profile／接入双方；通过轨道格式和内容契约声明，不能以批次名义允许同轨同周期多个独立数据帧 |
| 一次输出如何开始或结束、是否需要输出标识、标识字段和关联范围 | Profile；Core 不强制 `generation_id`，也不要求统一的生成状态机 |
| 领域任务的标识、阶段、回执及并发规则 | Profile；可选择连续指针操作或其他任务模型 |
| system 必选且唯一、单向输入路由、可信来源及通用封装 | Core；按整个会话配置统计 `role=system`，不规定通知载荷的事件集合或内容 Schema |
| 唯一 system 轨道使用哪个信息同步组、与哪些内容同步交付 | Profile；可同组，也可独立，需要及时通知时推荐独立信息同步组 |
| system 事件名称、字段、必填项、语义、目标及通知阶段 | Profile；内容 Schema 通过格式声明提供，实际处理由协调器／适配器执行 |

Profile 可以用自定义事件、工具调用或格式中的结束标记表达输出边界和请求，也可以采用连续流而不划分生成轮次。system 通知的内容也由 Profile 自行定义，Core 不保留任何统一的系统事件或 assistant 结束事件名称。服务端按已确认的 Profile 解释内容，通过运行时机制更新会话状态，并按该 Profile 发布通知；Core 不因载荷中出现某个字段或名称就关闭会话或切换配置。身份、epoch、配置生效及历史隔离等通用约束仍然有效，不能被通知载荷覆盖。

采用相同 A2RT 核心并不自动保证双方理解相同的系统通知，接收方需要确认兼容的 Profile 及其内容格式。以后可提供可选公共 Profile 复用常见通知，不将其事件名称或 Schema 提升为强制核心标准。

Profile 自行声明 assistant 内容契约的版本、格式及处理规则。通用消息与领域内容之间可以保留关联，不能据此把领域事件类型、任务字段或生成标识提升为核心必填字段。

## 2. 四项职责的划分

| 事项 | Core 提供的通用机制 | Profile 定义的具体规则 |
| --- | --- | --- |
| 播放与呈现 | 共同时间坐标、窗口和关联标识，承载呈现位置及实际结果 | 立即呈现或缓冲后播放、内容时间到播放时刻的映射、音画关联、迟到动作及设备能力要求 |
| 超时与恢复 | 超时/缺失状态、缺口与通用关联、system 通知承载、epoch 隔离 | 系统通知与模型侧恢复请求的契约、等待预算如何起算、补交或跳过、重试范围与期限、消费位置如何推进、何时暂停/结束/切换 epoch |
| 同步完整性 | 同组共同窗口、接收端成员关系、缓存与交付状态，承载完整/部分/失败及缺失说明 | 参与来源、何时算收齐、空值/保持是否有效、媒体是否必须解码、状态与画面是否一致、何时允许决策 |
| 内容校验 | `media_type + constraints` 声明、格式引用与协商结果、Schema 内联/引用互斥、错误关联 | 内容 Schema 的版本与校验方式、格式验证、业务值有效性、校验时机与失败处置 |

Core 检查协议封装和通用不变量；Profile 实现检查内容并报告结论。二者可以位于同一个进程或共享代码，但规范职责保持区分。Core 不要求内置每种媒体解码器、业务验证器或某一种 JSON Schema 校验库。

## 3. 播放与恢复

信息同步组提供内容定位和同步分组，不自动决定扬声器、画面或执行器何时动作。Profile 可以采用缓冲后的共同呈现起点，也可以采用满足其场景要求的其他调度策略；适配器保留来源时间及实际呈现事实，不能用实际播放时间覆盖原采集时间。

超时也不自动意味着丢弃、重放或暂停。Profile 可以定义补交、跳过、部分交付、暂停、终止或新 epoch 等行为，并约定相关位置及状态怎样更新。Core 提供这些行为所需的身份、引用、缺失与控制机制，不规定唯一恢复算法，也不统一要求从上一次消费点重新采集。

固定 `frame_seq` 仍标识固定窗口。Profile 如果批量补交多个窗口，应保留各窗口原有身份和时间，每条轨道在每个窗口仍最多一个数据帧；不能把补交内容都记入当前周期或为已有位置追加第二帧。切换 epoch 应保留旧配置的解释。恢复产生新的交付或控制记录，不把旧失败记录修改成曾经成功，不以恢复名义替换已提交的数据帧，也不把旧副作用当作新请求重新执行。具体是否允许补交、重试及何时停止，由 Profile 决定。

第 01 章的 `delivery_policy.max_wait_root_ticks`、`delivery_policy.max_skew_root_ticks`、`delivery_policy.on_timeout` 是承载 Profile 策略的配置位置：Core 统一刻度和引用方式，Profile 规定等待起点、对齐对象与动作含义。示例中的 `suspend`、`deliver_partial` 不构成 Core 的封闭策略枚举。

系统事件由可信协调器经唯一的 system 输入轨道通知，其名称、Schema、含义及实际处理由 Profile 和相应实现确定。若 Profile 定义模型结束标记、取消或结束会话请求，它们经 assistant 输出轨道发布。领域输出结束不自动证明剩余音频已播放或活动任务已完成；请求也不等于会话结束，实际结束由协调器确认后按所选 Profile 的系统通知契约表达。Profile 可让通知与媒体同组同步交付，也可选择独立信息同步组；实际中断、关闭和清理不应等待通知交付后才开始，具体调度与恢复仍由 Profile/Binding 约定。

## 4. 信息同步组与完整性判断

同一信息同步组表示内容按照共同窗口组织和同步交付，不意味着 Core 理解窗口中的业务内容。适用于某接收端的轨道范围由方向和来源绑定确定；窗口是否满足交付条件，由该接收端的 Profile 实现判定。不同信息同步组继续独立推进。

信息帧属于信息同步组；其中不同轨道各自最多贡献一个数据帧，并分别通过 `track_id` 引用该组内的轨道。Core 检查 `sync_group_id` 与成员引用、信息同步组归属及每轨每周期唯一性；这一上限跨消息、来源和方向共同生效，Profile 不能覆盖。Profile 决定这些数据帧在何种条件下构成完整观察；不能用一个信息帧级的 `track_id` 代替全部成员。同一个时钟供多个同步组复用时，各组仍独立交付。

例如 Canvas 可以将环境音频、画面和状态放在同一信息同步组，并要求音频覆盖该窗口、画面来自指定状态快照。只有 Canvas 适配器确认这些关系后，才报告该窗口符合其完整性交付条件。Core 根据该结果推进通用交付状态，不自行检查元素版本或重新渲染画布。

整帧清单、不同轨道分别到齐后的完整性确认、分片重组结果、来源水位等，都是 Profile/Binding 可以选择的实现方式。它们不允许同一轨道在同周期追加、替换或逐次发布多个数据帧；同一原帧的分片与重传按原身份处理。Core 不强制新增统一的“窗口结束事件”，也不规定所有场景采用同一个业务事件计数算法。

完整性的阶段也由 Profile 明确：存储转发场景可以以完整编码资源为目标；向模型开放媒体的场景可以要求已解码、可消费。网络包收齐、内容校验通过、模型已消费和用户已听到是不同事实，不能相互冒充。Profile 可以允许部分交付，但应按约定表达部分或缺失，不能暗中改写完整性的含义。

## 5. 内容声明与内容校验

`media_type` 选择内容格式及其约束规则，`constraints` 承载双方声明的契约。标准字段的名称、单位和含义保持统一，实际内容由 Profile 指定的适配器、解码器或接收应用处理。承载或转发这些声明的 Core 不需要验证其中的业务值。

| 情况 | 责任归属 |
| --- | --- |
| 未声明的轨道、无效格式引用、同一配置里同时出现 `constraints.schema` 与 `constraints.schema_ref` | Core 的结构与引用校验 |
| JSON 的 `type`、`required`、`enum` 等声明是否被实际载荷满足 | Profile 指定的内容校验实现 |
| 邮箱格式是否检查、对象 ID 是否存在、工具参数在当前状态下是否允许 | Profile／应用的格式或业务规则 |
| 图片实际像素尺寸、音频实际编码及完整载荷是否满足声明上限 | Profile 指定的媒体处理器；通用传输预算仍由 Core／Binding 执行 |
| 校验失败后拒绝、报告缺口、请求新数据或进入恢复 | Profile 选择策略，Core 承载结果与控制 |

JSON 支持 `constraints.schema` 内联或 `constraints.schema_ref` 引用，二者互斥。Core 约束这两种表达的结构和选择方式；具体 JSON Schema 方言、`format` 是注解还是强制断言、引用如何解析及实际校验时机，由 Profile 定义。文档中的 Draft 2020-12 是示例，不是 Core 强制的全局校验配置。

下放责任不等于忽略已经声明的契约。参与方若声明支持某 Profile 及约束，应由约定的实现履行；仅转发的节点不必重复验证，也不能据此声称业务校验已经完成。未知能力、校验失败和暂未校验的处理由 Profile 明确，Core 不自动把它们等同于成功。

## 6. Profile 如何写明规则

一个 Profile 可以用文档明确名称与版本、轨道及格式用途，再分别描述以下内容：

- system 内容契约：为必选且唯一的 system 输入轨道选择信息同步组，定义通知事件、字段、Schema 版本、目标和阶段，以及同组时的空通知和完整性规则；说明如何与协调器维护的实际状态关联。
- assistant 内容契约：支持哪些事件／工具、参数结构、输出边界及是否采用输出标识，如何将请求映射为实际处理和系统通知。
- 播放：使用什么时间基准，何时呈现，怎样报告迟到与实际位置。
- 恢复：超时从哪里起算，允许哪些恢复动作，如何处理缺失窗口、消费位置和活动任务。
- 完整性：在每轨每周期最多一个数据帧的 Core 上限内，哪些来源和内容参与判断，何时可交付，部分内容和控制信息如何处理；双向或多来源轨道如何安排唯一发布方。
- 配置与限额：声明信息同步组及 `sync_group_id` 绑定，在 `delivery_policy` 中确认交付参数，在 `limits` 中确认组容量及各接收端队列上限；运行水位、积压量和状态另行记录。
- 内容校验：由谁校验哪些内容，使用何种 Schema/媒体规则，如何反馈失败。

这些是 Profile 的规范内容，不要求按条目增加固定的 Core 字段。适合协商的参数可放入机器定义，其余规则可以由版本化文档和适配器实现共同确定。

本项目的 Canvas 选择同步交付、每 actor 同时一个任务、按其状态与媒体规则判断完整观察；这些是 Canvas 的选择。其他 Profile 可以选择不同的呈现、恢复和校验方式，无需修改 A2RT 核心结构。

Canvas 配置六条领域轨道和唯一的 system 输入轨道，由 Canvas Profile 选择其信息同步组及通知内容契约；若定义模型结束标记，可复用 assistant 输出事件轨道，并自行约定名称、参数和输出标识。系统通知是否与领域媒体配齐取决于该 Profile 的信息同步组和完整性配置。具体适配要求见 [Canvas Profile](./profiles/canvas/README.md)。

## 7. 实现与验证边界

通用机制与 Profile 实现分别组织和验证：Core 检查封装、引用、时间映射、状态关联及预算；各 Profile 验证自己的播放、恢复、完整性和内容规则。某个 Profile 的具体事件、操作字段、采样调度或恢复流程，不自动成为所有 Profile 必须继承的核心要求。
