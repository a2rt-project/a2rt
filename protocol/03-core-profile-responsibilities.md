# Core、Profile 与 Binding 的职责边界

状态：当前架构设计草案；日期：2026-11-16。本章与[时钟、信息同步组及轨道](./01-clock-sync-group-track-model.md)、[媒体类型与约束](./02-media-types-and-negotiation.md)、[system 轨道与生命周期](./04-system-track-and-lifecycle.md)共同定义 Core、Profile、Binding 和实现方的职责。

A2RT 的定位是面向智能体与环境的实时业务信息交互协议。Core 规定通用的信息通道、时间组织和承载约束；Profile 规定某类应用的信息含义与交互条件；Binding 规定这些信息如何映射到具体通信方式。三者共同支持接收方消费符合约定的信息，职责以[协议定位](./README.md#协议定位与分层)为依据。

A2RT Core 提供通用承载、时间组织、交付状态，并要求每个会话配置必须且只能包含一条 system 单向输入轨道。Profile 选择该唯一轨道的信息同步组归属；system 和 assistant 的具体事件、参数、语义与内容 Schema，模型输出标识和输出边界，以及播放、恢复、同步完整性判断和内容校验，也由具体 Profile 定义，再由协调器、适配器或应用实现。不同场景可以采用不同策略；同一会话的参与方依据确认的 Profile 和配置协作，Core 不为未定义的业务规则猜测默认行为。

Binding 是具体承载方式的映射规范，明确序列化、消息封装、连接与来源绑定、分片重组、调度、容量和队列约束，并复用底层协议已有的传输能力。它落实 Profile 选择的通知与恢复方式，不能改变内容语义、放宽 Core 不变量，或将自己的控制消息提升为 Core 的必选接口。

发送端、接收端、适配器和运行时是实现这些规范的执行主体；Binding 本身不等同于某个独立服务。部署可以在同一进程内实现多层，也可以拆分服务。“谁发送谁负责”适用于每次信息交付，不因部署方式改变；播放、恢复、同步完整性和内容校验仍由 Profile 约定，运行时执行。

## 1. Profile 是什么

Profile 是基于 A2RT 的具体应用规范，例如 Canvas Profile、机器人控制 Profile 或传感器采集 Profile。它可以包含规范文档、机器可读的能力/配置及内容 Schema；实现代码由适配器或应用提供。Profile 不是必须由 Core 执行的脚本，也不要求把全部规则转换为 JSON 字段。

Profile 定义可复用的规则和允许的选择，会话配置确定本次采用的版本、参数及来源绑定。策略可以通过版本化规范或预先约定明确，不必逐帧重复传递。新增 Profile 不需要将领域字段加入 Core。

| 层次 | 负责 | 不承担 |
| --- | --- | --- |
| A2RT Core | 通用身份与配置引用、轨道及流向、时钟树与窗口、信息帧及其轨道数据帧引用、每轨每周期最多一个数据帧、格式声明、序号与关联、交付状态、system 必选唯一及单向输入约束、资源预算 | 强制错误控制消息、错误码或专用错误轨道；定义 system／assistant 事件枚举、内容 Schema 或模型输出标识；强制 system 独立信息同步组；根据载荷名称执行会话关闭等动作；决定播放、异常策略或业务内容有效性 |
| Profile | 唯一 system 轨道的信息同步组选择，system／assistant 事件、参数、语义及内容 Schema，输出标识与边界，呈现与恢复策略、同步完整性标准、校验责任、丢弃及通知方式、任务与领域规则 | 省略或重复 system 轨道；允许同轨同周期多个数据帧；改写 Core 的身份、时间坐标、配置版本和已记录事实 |
| 发送端／适配器 | 按 Profile 采集或接纳内容、切片、映射时间、拼装、对齐、校验与发送；负责信息交付质量，按选定策略承担发送侧纠错、重发、重新采集或失败处置 | 将信息准备与发送侧恢复责任转交给接收方或模型；把未交付报告成已经交付 |
| 接收端／接入层 | 完成必要的重组、去重、解码、校验和就绪判断；消费合格信息，执行约定操作，按 Profile 处理缺失或拒绝、按需通知并反馈实际业务结果，维护等待与消费位置 | 猜测或修补发送内容的业务含义；把网络到达、验收通过和执行成功混为一谈；要求模型完成传输恢复 |
| 模型 | 消费已就绪的观察，理解业务状态，输出音频、动作或其他 Profile 内容；根据业务执行结果作出下一步决策 | 实现 Binding，承担传输修复或信息交付前的预处理 |
| Binding | 定义具体承载映射，复用底层传输能力；由其实现落实序列化、封装、重组、完整性检查、连接与来源绑定，以及已确认的发送节拍、容量、队列约束和 Profile 选定的异常通知方式 | 改写 Profile 内容语义或放宽 Core 不变量；把传输成功直接等同于领域内容正确或用户已经看到/听到；将特定绑定的控制消息提升为 Core 必选接口 |

时钟与容量配置承担控制延迟和避免持续积压的职责，选取方式见[第 01 章 §2.3](./01-clock-sync-group-track-model.md#23-频率选取与调度落实)。Core 提供频率、标准帧单位和公共预算的表达与通用约束；Profile／部署根据实际能力确定目标工作范围和配置，Adapter／应用与 Binding 将其落实到生产、处理、发送及消费流程。具体调度算法和异常处置保持可配置，已确认的预算与期限则必须由相应实现履行。

信息同步组的配置按职责分为三部分：核心属性 `sync_group_id`、`clock_id`、`start_tick` 定义身份与窗口；`delivery_policy` 承载 Profile 选定的交付规则；`limits` 承载确认后的资源上限。`limits.max_frame_units` 约束整个组信息帧的编码容量，`limits.receiver_queues` 通过 `receiver_id` 分别约束各接收端队列的 `max_pending_frames`。这些限额由 Core／Binding 落实，Profile 不能绕过。分组只明确责任，不把容量或缓存上限变成可忽略的业务建议。

### 1.1 轨道内容契约与通用身份

| 内容 | 定义方 |
| --- | --- |
| 会话身份、epoch、轨道／信息帧引用、通用消息身份及关联 | Core；用于路由、时间组织、去重和引用，不解释为某次模型生成或工具任务 |
| 时钟整数刻度边界与信息帧窗口两端的根刻度整数对齐 | Core；允许整数偏移、不要求全部零点重合；Profile／Binding 不得放宽，也不能用舍入或内容对齐容差替代精确映射 |
| 每条轨道每个周期最多一个数据帧 | Core；所有来源和方向共享上限，Profile／Binding 不得豁免；分片和原帧重传不增加帧数 |
| assistant 事件名称、参数、工具调用／空事件表达及单帧载荷结构 | Profile／接入双方；通过轨道格式和内容契约声明，不能以批次名义允许同轨同周期多个独立数据帧 |
| 一次输出如何开始或结束、是否需要输出标识、标识字段和关联范围 | Profile；Core 不强制 `generation_id`，也不要求统一的生成状态机 |
| 领域任务的标识、阶段、回执及并发规则 | Profile；可选择连续指针操作或其他任务模型 |
| system 必选且唯一、单向输入路由、可信来源及通用封装 | Core；按整个会话配置统计 `role=system`，不规定通知载荷的事件集合或内容 Schema |
| 唯一 system 轨道使用哪个信息同步组、与哪些内容同步交付 | Profile；可同组，也可独立，需要及时通知时推荐独立信息同步组 |
| system 事件名称、字段、必填项、语义、目标及通知阶段 | Profile；内容 Schema 通过格式声明提供，实际处理由协调器／适配器执行 |

Profile 可以用自定义事件、工具调用或格式中的结束标记表达输出边界和请求，也可以采用连续流而不划分生成轮次。system 通知的内容也由 Profile 自行定义，Core 不保留任何统一的系统事件或 assistant 结束事件名称。服务端按已确认的 Profile 解释内容，通过运行时机制更新会话状态，并按该 Profile 发布通知；Core 不因载荷中出现某个字段或名称就关闭会话或切换配置。身份、epoch、配置生效及历史隔离等通用约束仍然有效，不能被通知载荷覆盖。

采用相同 A2RT 核心并不自动保证双方理解相同的系统通知，接收方需要确认兼容的 Profile 及其内容格式。以后可提供可选公共 Profile 复用常见通知，不将其事件名称或 Schema 提升为强制核心标准。

Profile 自行声明 assistant 内容契约的版本、格式及处理规则。通用消息与领域内容之间可以保留关联，不能据此把领域事件类型、任务字段或生成标识提升为核心必填字段。

### 1.2 面向模型的信息交付边界

**统一原则是“谁发送谁负责”：发送端负责将信息准备到符合 Profile 约定的可消费状态；接收端负责验收和消费。需要纠错与恢复时，发送端承担发送侧责任。** 异常策略由 Profile 选择，不强制每次失败都通知或重试。发送端与接收端按每次信息流向区分，同一参与方可以在两个方向上分别承担这两种职责，不将责任固定给环境端或模型端，也不增加轨道角色或方向字段。

| 信息方向 | 发送端责任 | 接收端责任 |
| --- | --- | --- |
| 环境 → 模型 | 环境侧适配器／协调器组织观察，完成采集、切片、时间映射、音画与状态关联及发送前校验；按选定策略处理发送侧恢复 | 模型侧接入层验收，按 Profile 丢弃或隔离缺失、冲突与过期内容，向模型开放符合约定的观察，按需通知问题 |
| 模型 → 环境 | 模型服务及其适配器接纳模型输出，组织音频、操作与时间关联，完成发送前检查，按选定策略处理发送侧恢复 | 环境侧接入层验收，按 Profile 处理异常、调度播放与执行，反馈约定的实际业务结果 |

这里的发送端是负责 A2RT 信息交付的逻辑端点，包含其适配器与运行时。多个采集源共同组成一个观察时，Profile 须明确负责最终拼装与交付的发送端协调器，不能让模型从未组织的源数据中自行拼装。模型作为内容生产者，不承担分包、重传或连接恢复工作。

接收端仍须进行必要的传输重组与内容验收；这不是接收端替发送端准备信息。发现缺失或不符合契约时，接收端按 Profile 丢弃、隔离、通知或采取其他约定措施。选择补交或恢复时，由发送端负责重发或重新采集；选择通知时，双方运行时使用约定的轨道或其他通道，不要求统一的错误消息。接收端维护真实的等待、拒绝、暂停及消费位置，不能猜测缺失内容或把修复工作交给模型。通知和恢复均不是 Core 的无条件义务。

验收通过不等于业务执行成功。接收端对实际消费与执行结果负责；当它发送执行结果或其他反馈时，又作为该反馈的发送端履行上述责任。

A2RT 为智能体处理的信息建立共同的时间、内容与交付契约。面向模型的交付单元必须已满足所选 Profile 的消费条件；声明一组轨道、附上时间戳或把网络包收齐，都不足以证明这一条件成立。Profile 定义条件，Core 提供通用机制，指定的适配器与运行时负责落实，模型负责消费结果。

文中的“智能体端”包括接入层与模型本身。数据到达智能体端的网络连接，与数据获准输入模型，是不同的处理阶段：

```text
环境数据源
  → 发送端：采集／切片、时间映射、信息拼装、Profile 校验
  → Binding：按约定节拍与容量传输
  → 模型侧接入层：重组／去重、必要的解码与校验、确认可消费
  → 模型：理解观察、推理、产生业务输出
```

1. **发送前组织信息。** 环境侧发送端负责将分散来源组织为 Profile 约定的观察，保留真实采集时间，并关联画面、音频、事件与状态。采用同步交付时，发送端先完成该契约要求的对齐和完整性检查。允许分片或逐轨传送，但这些传输步骤不改变模型入口的交付条件。
2. **接收后守住消费边界。** 发送前的准备不能消除途中断线、截断、重复或迟到。模型侧接入层验收并按 Profile 处理异常；若选择补交或重新采集，由环境侧发送运行时负责。未满足条件的内容在接入层被丢弃、隔离、等待或进入其他约定流程，不能作为正常观察直接投入模型。解码可以由接入层或模型服务的媒体组件完成；若模型接口原生接受某种编码格式，无需强制转换成另一种格式，但仍须满足其输入契约。
3. **以可消费单元持续交付。** 就绪可以针对一个音频片段、一个观察窗口或 Profile 允许的部分观察。部分交付须明确哪些内容缺失、哪些是保持的旧内容及其真实时间，不能伪装成完整的新观察。不同同步组独立推进，不因这条边界新增全模态、全会话屏障。
4. **区分传输故障和业务结果。** 丢包、重组失败、校验失败及重同步由双方运行时依上述发送与接收责任处理，不能要求模型发出重传、补包或连接恢复指令。若 Profile 选择向模型通知故障影响，应提供可理解的中断、不可用或部分观察状态。工具目标不存在、操作未成功等业务结果可以反馈给模型，由模型决定下一步；模型主动请求重新观察环境也可以是业务行为，不等同于修复传输缺口。
5. **恢复不冒充模型行为。** 适配器自动发起的传输恢复属于运行时控制，不能伪装成模型生成的 assistant 事件。具体机制由 Profile／Binding 定义，Core 不新增固定的恢复工具或事件名。Profile 选择发布结束或暂停等 system 通知时，仍由可信协调器发到唯一的 system 输入轨道；其他异常通知可按 §1.3 选择载体，通知与实际处理保持区分。

模型输入所需的时间、有效性和业务关联应按 Profile 保留；分片头、重试日志及内部排队状态不因存在于传输封装中就必须进入模型内容。反方向同样由适配器接纳、校验和组织模型输出，再交给环境执行，不能把未经检查的输出当作已经执行成功。

### 1.3 默认业务通道与异常处置

**A2RT 默认承载符合约定的业务数据，正常路径以发送方已完成信息准备和校验为前提。** 这项契约不承诺故障绝不发生，也不取消通用结构、身份、时间、容量和内容的必要校验。数据是否合格与发现不合格后如何处置是两个问题：Core 保留通用不变量，Profile 定义内容有效性与异常策略。

**Core 不强制定义错误控制消息、错误码、逐帧 ACK、补包请求、专用错误轨道或额外通知通道。** Binding 可以复用底层已有的可靠传输、连接状态与差错处理能力；需要额外通知或恢复时，由 Profile 约定并由运行时落实。文中的“拒绝”“缺失”“失败”和运行状态描述实际处理结果，不意味着必须发送某种同名消息。

| Profile 可以选择的方式 | 需要明确的约定 |
| --- | --- |
| 直接丢弃，不发送通知 | 丢弃数据帧还是整个观察窗口，缺口、依赖、消费位置与后续交付怎样处理 |
| 通过自定义轨道通知 | 轨道角色、方向、来源、同步组、格式、内容 Schema、接收者与触发条件；也可复用已约定用途的轨道 |
| 另建通知通道或使用其他通知方式 | 端点与来源身份、会话／epoch／目标关联、格式、触发条件、通知失败后的处置，以及是否向模型呈现 |
| 恢复、暂停或终止 | 谁执行、触发条件、期限和真实结果；是否发送通知及如何通知另行约定 |

通知轨道仍是普通 A2RT 轨道，须遵守配置、格式、来源、容量和每轨每周期最多一个数据帧的约束。若使用 `role=system`，只能复用会话中唯一的 system 输入轨道，不能因通知用途增加第二条或将其改为双向。其他角色的通知轨道按 Profile 声明，不得把运行时自动通知冒充模型实际生成的 assistant 内容。

轨道外通知不占 A2RT 轨道的数据帧位置，不自动具有某条轨道的角色、方向或同步保证；Profile／Binding 自行约定其契约。若与业务轨道共享传输或处理资源，部署仍须计入真实开销，不能视为免费容量，也不能借通知通道旁路传送业务数据、绕过交付条件或 Core 限额。

丢弃不等于成功交付、成功执行或新的有效空帧。Profile 须约定受影响同步组是等待、跳过、允许部分交付还是停止；缺失媒体不能伪装成当前画面或已知静音。保留旧画面时仍保留其真实时间和有效性，原帧重传保持身份与内容，新采集内容进入新的合法周期；不修改已发布数据或历史事实。Core 不要求为每次丢弃单独发消息，运行时仍须维护判断后续交付所需的真实状态。

合法的业务失败结果不等于协议异常。例如工具调用返回“目标不存在”，只要符合 Profile 的结果契约，就属于可消费的业务数据。Profile 选择发送的异常通知也必须先组织成符合其契约的信息；模型理解业务影响，运行时负责机械性的故障处置。

## 2. 四项职责的划分

| 事项 | Core 提供的通用机制 | Profile 定义的具体规则 |
| --- | --- | --- |
| 播放与呈现 | 共同时间坐标、窗口和关联标识，承载呈现位置及实际结果 | 立即呈现或缓冲后播放、内容时间到播放时刻的映射、音画关联、迟到动作及设备能力要求 |
| 超时与恢复 | 交付状态、窗口与通用关联、可用于通知的轨道机制、epoch 隔离；不强制错误控制消息 | 按“谁发送谁负责”明确发送侧修复与接收侧验收；选择丢弃、通知及其载体、等待起点、补交或跳过、重试范围与期限、消费位置及暂停/结束/切换 epoch；不要求模型修复传输 |
| 同步完整性 | 同组共同窗口、接收端成员关系、缓存与交付状态，承载完整/部分/失败及缺失说明 | 参与来源、何时算收齐、空值/保持是否有效、媒体是否必须解码、状态与画面是否一致、何时允许决策 |
| 内容校验 | `media_type + constraints` 声明、格式引用与协商结果、Schema 内联/引用互斥、通用身份与关联 | 内容 Schema 的版本与校验方式、格式验证、业务值有效性、校验时机，以及失败后的丢弃或其他处置、是否通知及其方式 |

Core 检查协议封装和通用不变量；Profile 实现检查内容并据此决定交付，是否对外报告按其异常策略执行。二者可以位于同一个进程或共享代码，但规范职责保持区分。Core 不要求内置每种媒体解码器、业务验证器或某一种 JSON Schema 校验库，也不因校验失败强制发送控制消息。

## 3. 播放与恢复

信息同步组提供内容定位和同步分组，不自动决定扬声器、画面或执行器何时动作。Profile 可以采用缓冲后的共同呈现起点，也可以采用满足其场景要求的其他调度策略；适配器保留来源时间及实际呈现事实，不能用实际播放时间覆盖原采集时间。

超时也不自动意味着丢弃、重放或暂停。Profile 可以定义丢弃、补交、跳过、部分交付、暂停、终止或新 epoch 等行为，并约定相关位置及状态怎样更新。Core 提供这些行为所需的身份、引用、时间和交付状态，不强制恢复算法、控制消息或通知载体，也不统一要求从上一次消费点重新采集。

固定 `frame_seq` 仍标识固定窗口。Profile 如果批量补交多个窗口，应保留各窗口原有身份和时间，每条轨道在每个窗口仍最多一个数据帧；不能把补交内容都记入当前周期或为已有位置追加第二帧。切换 epoch 应保留旧配置的解释。恢复产生新的交付或控制记录，不把旧失败记录修改成曾经成功，不以恢复名义替换已提交的数据帧，也不把旧副作用当作新请求重新执行。具体是否允许补交、重试及何时停止，由 Profile 决定。

第 01 章的 `delivery_policy.max_wait_root_ticks`、`delivery_policy.max_skew_root_ticks`、`delivery_policy.on_timeout` 是承载 Profile 策略的配置位置：Core 统一刻度和引用方式，Profile 规定等待起点、对齐对象与动作含义。示例中的 `suspend`、`deliver_partial` 不构成 Core 的封闭策略枚举。

系统事件由可信协调器经唯一的 system 输入轨道通知，其名称、Schema、含义及实际处理由 Profile 和相应实现确定。若 Profile 定义模型结束标记、取消或结束会话请求，它们经 assistant 输出轨道发布。领域输出结束不自动证明剩余音频已播放或活动任务已完成；请求也不等于会话结束，实际结束由协调器确认后按所选 Profile 的系统通知契约表达。Profile 可让通知与媒体同组同步交付，也可选择独立信息同步组；实际中断、关闭和清理不应等待通知交付后才开始，具体调度与恢复仍由 Profile/Binding 约定。

## 4. 信息同步组与完整性判断

同一信息同步组表示内容按照共同窗口组织和同步交付，不意味着 Core 理解窗口中的业务内容。适用于某接收端的轨道范围由方向和来源绑定确定；窗口是否满足交付条件，由该接收端的 Profile 实现判定。不同信息同步组继续独立推进。

信息帧属于信息同步组；其中不同轨道各自最多贡献一个数据帧，并分别通过 `track_id` 引用该组内的轨道。Core 检查 `sync_group_id` 与成员引用、信息同步组归属及每轨每周期唯一性；这一上限跨消息、来源和方向共同生效，Profile 不能覆盖。Profile 决定这些数据帧在何种条件下构成完整观察；不能用一个信息帧级的 `track_id` 代替全部成员。同一个时钟供多个同步组复用时，各组仍独立交付。

例如 Canvas 可以将环境音频、画面和状态放在同一信息同步组，并要求音频覆盖该窗口、画面来自指定状态快照。只有 Canvas 适配器确认这些关系后，才报告该窗口符合其完整性交付条件。Core 根据该结果推进通用交付状态，不自行检查元素版本或重新渲染画布。

整帧清单、不同轨道分别到齐后的完整性确认、分片重组结果、来源水位等，都是 Profile/Binding 可以选择的实现方式。它们不允许同一轨道在同周期追加、替换或逐次发布多个数据帧；同一原帧的分片与重传按原身份处理。Core 不强制新增统一的“窗口结束事件”，也不规定所有场景采用同一个业务事件计数算法。

完整性的阶段也由 Profile 明确：存储转发场景可以以完整编码资源为目标；向模型开放媒体时，必须达到该模型接口及 Profile 约定的可消费阶段，具体是否预先解码取决于格式契约。网络包收齐、内容校验通过、模型已消费和用户已听到是不同事实，不能相互冒充。Profile 可以允许部分交付，但应按约定表达部分或缺失，不能暗中改写完整性的含义，也不能将剩余的传输整理工作交给模型。

## 5. 内容声明与内容校验

`media_type` 选择内容格式及其约束规则，`constraints` 承载双方声明的契约。标准字段的名称、单位和含义保持统一，实际内容由 Profile 指定的适配器、解码器或接收应用处理。承载或转发这些声明的 Core 不需要验证其中的业务值。

| 情况 | 责任归属 |
| --- | --- |
| 未声明的轨道、无效格式引用、同一配置里同时出现 `constraints.schema` 与 `constraints.schema_ref` | Core 的结构与引用校验 |
| JSON 的 `type`、`required`、`enum` 等声明是否被实际载荷满足 | Profile 指定的内容校验实现 |
| 邮箱格式是否检查、对象 ID 是否存在、工具参数在当前状态下是否允许 | Profile／应用的格式或业务规则 |
| 图片实际像素尺寸、音频实际编码及完整载荷是否满足声明上限 | Profile 指定的媒体处理器；通用传输预算仍由 Core／Binding 执行 |
| 校验失败后丢弃、通知、请求新数据或进入恢复 | Profile 选择策略及通知方式；Core 提供通用关联，不强制错误控制消息 |

JSON 支持 `constraints.schema` 内联或 `constraints.schema_ref` 引用，二者互斥。Core 约束这两种表达的结构和选择方式；具体 JSON Schema 方言、`format` 是注解还是强制断言、引用如何解析及实际校验时机，由 Profile 定义。文档中的 Draft 2020-12 是示例，不是 Core 强制的全局校验配置。

下放责任不等于忽略已经声明的契约。参与方若声明支持某 Profile 及约束，应由约定的实现履行；仅转发的节点不必重复验证，也不能据此声称业务校验已经完成。未知能力、校验失败和暂未校验的处理由 Profile 明确，Core 不自动把它们等同于成功。

## 6. Profile 如何写明规则

一个 Profile 可以用文档明确名称与版本、轨道及格式用途，再分别描述以下内容：

- system 内容契约：为必选且唯一的 system 输入轨道选择信息同步组，定义通知事件、字段、Schema 版本、目标和阶段，以及同组时的空通知和完整性规则；说明如何与协调器维护的实际状态关联。
- assistant 内容契约：支持哪些事件／工具、参数结构、输出边界及是否采用输出标识，如何将请求映射为实际处理和系统通知。
- 播放：使用什么时间基准，何时呈现，怎样报告迟到与实际位置。
- 发送与接收责任：逐方向明确负责最终信息单元的发送端、发送前准备与校验、接收验收条件及异常处置；多个来源共同构成观察时明确发送端协调器。
- 异常与通知：哪些情况直接丢弃、丢弃范围和同步组后续如何推进；是否通知、接收者及内容；选择自定义轨道、另建通知通道或其他方式时明确其契约和失败处置，不默认新增 Core 错误消息。
- 恢复：若选择恢复，明确超时从哪里起算，发送端如何补交、重新采集或处置无法交付，接收端如何隔离缺失窗口、维护消费位置，双方如何处理活动任务及业务影响；通知按上述策略执行，不依赖模型发出传输恢复请求。
- 模型入口：发送端预先组织哪些信息，接入层检查什么，满足什么条件才向模型开放；区分正常观察、允许的部分观察、业务执行失败与内部传输故障。
- 完整性：在每轨每周期最多一个数据帧的 Core 上限内，哪些来源和内容参与判断，何时可交付，部分内容和控制信息如何处理；双向或多来源轨道如何安排唯一发布方。
- 配置与限额：声明信息同步组及 `sync_group_id` 绑定，在 `delivery_policy` 中确认交付参数，在 `limits` 中确认组容量及各接收端队列上限；运行水位、积压量和状态另行记录。
- 内容校验：由谁校验哪些内容，使用何种 Schema/媒体规则，失败后如何处置及是否通知。

这些是 Profile 的规范内容，不要求按条目增加固定的 Core 字段。适合协商的参数可放入机器定义，其余规则可以由版本化文档和适配器实现共同确定。

本项目的 Canvas 选择同步交付、每 actor 同时一个任务、按其状态与媒体规则判断完整观察；这些是 Canvas 的选择。其他 Profile 可以选择不同的呈现、恢复和校验方式，无需修改 A2RT 核心结构。

Canvas 配置六条领域轨道和唯一的 system 输入轨道，由 Canvas Profile 选择其信息同步组及通知内容契约；若定义模型结束标记，可复用 assistant 输出事件轨道，并自行约定名称、参数和输出标识。系统通知是否与领域媒体配齐取决于该 Profile 的信息同步组和完整性配置。具体适配要求见 [Canvas Profile](./profiles/canvas/README.md)。

## 7. 实现与验证边界

通用机制与 Profile 实现分别组织和验证：Core 检查封装、引用、时间映射、状态关联及预算；各 Profile 验证自己的播放、恢复、完整性和内容规则。某个 Profile 的具体事件、操作字段、采样调度或恢复流程，不自动成为所有 Profile 必须继承的核心要求。

面向模型的实现还应验证消费边界：截断与重复内容不会作为新观察进入模型；同步 Profile 不交付未经确认的音画／状态组合；超时由运行时处理且无需模型调用恢复工具；允许的部分观察具有明确缺失说明；业务执行失败按契约可见；原帧重传不产生新的业务帧身份或改变原帧时间。这些检查验证信息是否已组织好，不能由“网络传输成功”替代。
